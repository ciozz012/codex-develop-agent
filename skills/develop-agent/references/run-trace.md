# 用一次运行记录解释 Agent 为什么停下

从一个具体问题开始，例如“查件工具已经拿到签收回执，为什么用户只收到‘查询次数用完了’？”在项目已有的日志或追踪系统中，先锁定这次请求的运行标识，再沿实际执行路径取证。

## 在哪里留下什么

| 记录位置 | 排查提前停止时需要的最少信息 |
|---|---|
| 接到任务 | 本次运行标识、目标对象的代号、用户需要的结果和完成凭据。记录生效的规则版本及相关上限，便于还原当时的约定。 |
| 调用模型或工具 | 给每次实际调用一个标识，关联发起它的事件，记录动作、起止时间和结果状态。重试分别计次，关联同一业务操作。用脱敏摘要或带版本的记录引用说明这次取得了哪些业务事实。 |
| 执行层作出决定 | 当场写下动作（继续、等待、结束等）、命中的规则、决策实际读到的结果标识、仍缺的凭据，以及影响该分支的额度或截止时间。若判定无法继续，记下当时可用的下一步及阻塞条件。保留执行时对缺口的判断，供排查时与原始证据核对。 |
| 对外答复或暂停 | 记录交付状态和用户可见答复的脱敏摘要。暂停时记下等待什么、已登记的唤醒或接续标识。若只有生成好的答复，向用户发送是否成功仍待核实。 |

复用现有运行标识（如 trace ID）关联各步骤，给关键事件留可引用的编号。并发时按调用标识配对请求与结果。如果模型参与选择动作，分别记下它提出的工具调用或结束信号，以及执行层实际派发或拦下的动作。工具完成、结果进入决策输入、决定生效是三个不同的时点。同一聊天里的另一轮、决定之后才到的结果，都要按各自的归属处理。异步恢复跨越多次运行时，用任务号和前一次运行的引用衔接。[OpenTelemetry 的追踪模型](https://opentelemetry.io/docs/concepts/signals/traces/)

用允许记录的字段生成摘要，在落盘或发送前剔除身份令牌、个人资料和无关业务正文。需要定位原文时，可引用受原有访问控制保护的记录及其版本。决策依据取自程序实际选择的分支和它读取的业务字段，避免让模型事后补写理由。[Langfuse 的追踪实践](https://langfuse.com/docs/observability/best-practices) · [采集时脱敏](https://langfuse.com/docs/observability/features/masking)

## 用一条记录定位

下面四步属于同一合成运行 R7。用户要的是包裹 P 的签收回执号，规则 v3 要求先核验已返回的证据，再判断还能否发起新调用。

| 事件 | 当时留下的记录 |
|---|---|
| E1 收到任务 | 对象 P，必需字段为回执号，工具调用上限 1 次。 |
| E2 工具返回 | 本次调用 C1 成功，取得 P 的回执号 RC-17。 |
| E3 执行层结束运行 | 决策输入含 E2 和 RC-17，剩余调用数 0，实际命中“次数用尽”，仍将回执号记为缺失。 |
| E4 答复已发送 | 用户收到“查询次数已用尽，未能确认回执号”。 |

最早可确认的错误在 E3。E2 已有回执，E3 也读到了它，却按额度用尽结束。先核对 E3 的完成判定。若记录里只有 E2 和 E4，就只能确认工具拿到了回执、答复没交付它。要查明原因，需补 E3 当时读取的结果和命中规则。采样、导出中断或最后一条事件缺失时，也应把不能确认的环节标为待核实。

## 怎样验收

在隔离环境从正常任务入口运行一个案例，把脱敏记录单独交给没参与实现的人。让对方指出用户要什么、决定前实际可用的证据、哪项仍缺、实际命中哪条规则、最终交付了什么，并为判断标出事件。再隐去决策事件，检查对方能否准确说明缺了什么证据。给 Codex 的本轮交付限定为定位结论、事件依据和最小补录点，修复逻辑另开一轮。
