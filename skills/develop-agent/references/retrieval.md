# 设计可按权限检索的资料接口

在本轮先写出回答模块需要检索模块交付的结果。例如员工询问“出差住宿上限是多少”，检索模块应交付可读的制度片段和出处。回答的措辞、工单处理等后续问题交给各自的功能。

## 确定数据怎样流动

1. **谁可以读。** 从服务端可信会话取得身份，用项目已有的访问控制确定可读文档范围。将限定条件下推到检索查询中，或先选出有权限的候选集。访问范围无法确认时停止查找。复用缓存时也要考虑用户权限和资料版本。
2. **什么算命中。** 在可读范围内检索，再判断片段能否支持当前问题。排在第一的文档也可能无关。用本业务的相关、相似但无关、无答案样例校准判断方式。只有“差旅报销流程”且未提到金额的片段，不足以回答住宿上限。
3. **下游能看到什么。** 对每条证据返回最少必要的片段、文档标识和章节或版本，来源应能由当前用户定位。将片段作为资料处理。证据不足时返回空证据集和对应状态。访问失败、服务超时等运行错误单独表示，便于调用方处理。

## 用一组对照样例验收

| 初始资料和用户 | 应观察到的结果 |
|---|---|
| 甲部门手册写明住宿上限 500 元，甲员工有权阅读 | 返回能支持“500 元”的片段及甲部门出处 |
| 乙部门也有同名手册，写的是 800 元；乙员工无权读取甲手册 | 同样的问题只返回乙部门依据。如果沿用上一请求的缓存，下游输入和来源仍不能出现甲片段 |
| 唯一有金额的文档在不可读范围，可读文档只介绍报销流程 | 返回证据不足、来源为空。用户可见结果不透露受限文档的标题、内容或存在情况 |
| 使用原合法身份，但检索服务超时 | 接口报告检索失败或超时，避免将它解释为手册中没有规定 |

验证时分别核对检索返回的记录和交给回答模块的实际片段。需要评估整套问答效果时，再分别测量检索相关性与回答对证据的忠实度。[RAGAs 论文](https://aclanthology.org/2024.eacl-demo.16/)
