# 把一次已定位的故障变成回归用例

先从项目已有测试入口找到处理这项业务的代码。用一句话写清正确行为，依据取自业务约定和权威结果。例如“本次查询只允许一次。作出结束决定时，若已经读到目标工单的回执，就把该编号交给用户。”故障记录用来还原触发条件，其中的错误答复不能充当预期答案。

## 保留一对能区分对错的场景

选出这次故障成立所必需的条件，并给它配一个原本正确的对照。下面两次都查同一张合成工单，工具都只调用一次，第 10 毫秒作决定时额度都已用完。两例仅改变回执进入决策输入的时机。

| 场景 | 受控输入 | 从用户收件箱及工具边界核对 |
|---|---|---|
| 已读到回执却没交付 | 第 3 毫秒工具返回并送入执行层，回执号由这次查询的数据给出 | 用户收到一次该工单的实际回执号，查询总数为 1。换一个合成编号也应交付对应值。 |
| 回执确实迟到 | 第 10 毫秒尚无回执，第 12 毫秒工具才返回。按本例约定，截止后任务结束 | 截止时只交付一次“未能确认”的结果。再推进到回执到达并处理完，收件箱仍只有原答复，查询总数仍为 1。 |

从正常业务入口运行待测判断。用合成数据替换个人信息和令牌，用可控时钟或明确的事件顺序替代真实等待。只替换外部依赖，保留决定、交付及迟到回调的实际执行路径。输入中只放用户请求、初始状态和工具会返回的事实，将正确答案和判定逻辑留在测试端。比较收件箱中实际交付的状态、编号和次数，允许等价措辞。历史日志可帮助找到故障，单纯重读旧日志无法验证当前代码。[Go 团队的时间相关测试实践](https://go.dev/blog/testing-time) · [Anthropic 的 Agent 评测方法](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

## 用同一套检查验证修复

1. 先在隔离的故障版本运行两例。应观察到早到用例因交付结果不符而失败，迟到对照通过。若两例都通过，检查测试是否经过出错的入口、是否真的读了用户收到的内容。若失败缘于导入或环境问题，先修好测试环境再取证。
2. 授权修复时，在候选版本使用相同的输入、期望和验证命令，两例都应通过。只受托补测试时，在展示故障和对照后停下，把失败断言交给修复会话。故障版本无法运行时，标明“旧版本未验证”，另列已有的运行证据。
3. 把用例放到项目已有的对应测试集中，交接测试入口、复跑命令、两个版本的逐例结果和覆盖范围。这里验证的是执行层的确定性行为。若故障取决于模型选择或措辞，将脱敏样本放入项目的行为评测集，按相同版本和配置重复运行，报告成功次数和失败样例。

## 复跑本例

从本技能目录运行下面两条命令。[离线回执示例](../examples/receipt_regression.py) 仅需 Python 3 标准库。两次使用同一个模拟查询入口和同一组断言，只切换结束判定的版本。第一条应返回失败，指出早到回执没有交付，同时迟到对照通过。第二条应全部通过。迁入业务项目时，把入口和收件箱换成项目对应的实现。

```text
python examples/receipt_regression.py --version faulty
python examples/receipt_regression.py --version fixed
```
