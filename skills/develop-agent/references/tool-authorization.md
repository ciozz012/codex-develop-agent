# 设计一个工具的身份与权限

选一个具体动作，沿调用路径写清“谁代表谁、对哪个资源、可以做什么、由哪一层裁决”。先查项目已有的登录会话、授权服务和数据访问层。用下列问题确定这个工具的权限边界。

| 设计问题 | 例：员工手册检索 |
|---|---|
| 谁在请求，工具代表谁？ | 工具从已验证的服务端会话取得员工身份和当前租户，助手代该员工检索。模型只传查询条件。若由后台任务发起，应另行确定任务自身的身份和获准范围。 |
| 可以执行什么动作？ | 工具执行入口检查该身份能否在此租户检索手册。服务账号即使能读取整个索引，此次请求也只使用当前员工获准的范围。 |
| 可以访问哪些资源？ | 按租户和项目已有的文档授权规则限定候选集，例如文档的可读用户或组。部门同名、获得工具使用权或拿到文档编号，都不足以说明有权读取这份文档。 |
| 哪些地方必须用同一项判断？ | 查询时应用范围约束，只有获准的片段才能送入后续模型或出现在引用中。按编号读取原文、打开引用、复用缓存时也按当前授权判断。 |

## 画清两道检查的位置

从服务端的受信上下文取得主体和委托范围。模型参数、用户自述和检索资料中的身份声明只作业务输入，不能扩大授权。缺少可信身份、无法确定授权或授权服务故障时，停止受保护的访问；向调用方区分“需登录”“动作未获准”“暂时无法核验”。有搜索权限但查不到可见文档时，走普通空结果，避免透露受限文档的标题或存在性。

将动作检查放在工具执行入口，将资源检查放在真正读取记录的服务或数据访问层。已有网关、策略引擎或数据库行级权限能提供同样保证时直接复用。跨服务采用 OAuth 的项目要核对令牌是否面向目标资源服务以及是否覆盖该动作；文档本身的授权仍由资源服务判定。缓存命中也要满足同一范围，可重新核验候选记录或绑定能随权限变更失效的授权版本。[RFC 9700 §2.3](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.3) · [OWASP 授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

## 用同一查询核对允许与拒绝

准备两家租户的同名部门、两位同部门但文档权限不同的员工，以及能区分来源的合成片段。设计阶段列出观察点，实施验收时从正常工具入口发起请求。

| 用例 | 需要核对的证据 |
|---|---|
| 员工有搜索权限且能读目标手册 | 工具结果、模型实际接收的片段和最终引用都只含获准来源；用员工身份能打开引用。 |
| 未登录、无搜索权限或授权服务无法完成判断 | 检查各自的返回状态，确认没有执行受保护的资料查询、没有向模型发送手册片段。 |
| 换到另一租户的同名部门，或换到同租户但无该文档权限的员工 | 对同一查询核对返回记录和传给模型的片段；受限记录的编号、标题和正文均未暴露。对已知来源链接也核对访问结果。 |
| 原用户查询成功，随后文档授权撤销 | 在授权变更生效后用同一会话、原查询和原链接重试，检查缓存、模型输入与引用均遵循新范围。 |

验收时记录授权决定、测试用的主体与资源代号、受保护读取次数及传入模型的合成片段标记。单看最终答复无法证明中间环节未收到受限内容。令牌和真实手册正文应留在其受控环境中。
