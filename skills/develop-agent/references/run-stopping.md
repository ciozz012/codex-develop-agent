# 设计单次业务任务的停止条件

先写下用户要的结果和能证明它的证据。以查件为例，用户问“包裹现在到哪了”，一条最新的中转记录就能回答。用户要求“等签收后告诉我谁签的”，同一条记录只说明包裹还在路上。工具返回成功、模型给出结语，都要按本次目标核对。

## 每次工具返回后怎样决定

| 观察到的业务事实 | 执行层的下一步 |
|---|---|
| 已取得全部必需证据 | 交付结果和依据，结束运行。最后一次允许的调用恰好给出证据，也应判为完成。 |
| 缺少证据，现有权限下还有能填补缺口的具体动作 | 继续。例如列表只有摘要，返回的回单号可以用来读签收详情。说明这个动作可能补齐什么。 |
| 服务明确正在处理，或只读调用遇到可恢复的暂时故障 | 记录已有的任务号和服务给出的最早查询时间。若只有短暂故障信号，按项目的退避规则延后重试。到时或收到有效事件后，在剩余预算内再查。同步等待行不通时，交付当前状态和恢复条件。只有系统确有唤醒机制时才承诺稍后通知。 |
| 存在歧义或缺必要输入，而且只有用户能补齐 | 先完成已有证据支持的部分，只问一个能解除阻塞的问题，例如“你要查哪张运单？” 保存已查到的结果，收到所需信息后再接续。 |
| 再调用也无法增加与目标有关的信息 | 结束本次运行，报告已确认的事实和仍然缺少的证据。例如“最近一条扫描在东站，目前无法确认签收人”。只有确实存在新的数据源、输入或事件时才给出相应的恢复方式。 |

**怎样识别空转。** 比较同一业务对象、实质相同的参数和已经取得的证据。响应时间、请求号、文字顺序发生变化，或两个工具交替返回同一条扫描，都没有补齐缺口。反过来，分页游标指向尚未读取的一页、出现新的签收回单，或异步服务规定的等待时间已到，都能成为下一次调用的理由。按业务判断有无进展，无须等到重复满固定次数才停。

## 让执行层管住最后一次调用

按任务约定最大调用次数和截止时间，并说明计数单位。模型轮数与工具调用次数可以不同，一轮可能发出多次调用。发起下一批调用前检查取消状态、时限和剩余额度，并发调用也须先占用各自的额度。已经返回的结果先对照完成条件。额度用尽且证据仍不全时，交付已知部分及停止原因。用户取消后停止派发新动作，对已发出的操作只陈述能确认的状态。外部写入的结果仍未知时，保留原操作号和待确认状态。

等待用户或服务时，记录当前目标和对象、还缺什么、已有证据、恢复所需的事件，以及剩余次数和截止时间。恢复时沿用这份记录。若用户把运单 A 更正为 B，沿用本次任务的剩余额度，迟到的 A 签收凭证只能用于 A。任务取消或结束后，旧通知不能自行重开任务。[Anthropic 的 Agent 设计实践](https://www.anthropic.com/research/building-effective-agents) · [OpenAI Agents SDK 的轮数定义](https://openai.github.io/openai-agents-python/ref/run/)

## 怎样验收

在同一条查件轨迹上更换用户目标，核对“查询当前状态”会立即交付，“等待签收人”会按工具约定等待或说明缺少什么。再把签收凭证放在最后一次允许的调用里，与最后一次仍只有中转记录作对照。记录实际调用顺序和次数、停止原因、用户可见答复，以及暂停后能否从原处接续。结束或等待期间多发一次无依据的调用，也要在验收中指出。
