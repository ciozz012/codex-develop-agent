# 按项目选择实现方式

用在当前功能第一次选型，或用户、业务规则、数据来源、可用工具发生了足以改变选择的变化时。沿用项目已有的需求、入口和测试。把结论写进当前任务条目即可。

## 哪一个事实会改变选择

拿项目里的一条请求，走一遍现行做法。记录使用者想得到什么、现行做法卡在哪一步，以及选错的具体后果。若项目已有人工流程、规则或线上版本，就用它作比较基线。新项目可用人工认可的样例或简单实现作起点，并标明效果待测。只追问会改变本轮选择的未知项。

| 当前功能中可观察的条件 | 值得先比较的做法 | 用什么结果检验 |
|---|---|---|
| 业务规则能将受支持的输入映射到已知分支，并定义异常输入如何处理，例如按数值区间分流 | 保留规则或普通代码。如用户已指定用模型，说明它负责的环节，仍保留规则基线 | 用同一组输入核对输出和例外分支；有响应时限时测完整入口 |
| 需要理解自由文本，但资料来源、执行顺序和允许返回的结果已知 | 固定流程，只在识别、抽取或组织答案的环节调用模型；需要可追溯事实时给模型可读依据 | 用代表性输入查关键事实、来源和依据不足时的答复，同时记录实际模型调用数 |
| 有多条合理路径，后续动作取决于刚取得的结果，已知分支难以覆盖代表性任务 | 先判断新增明确分支能否解决。仍需灵活选择时，让模型在获准的动作中选下一步，写明预算、结束或转人工的条件 | 用同一任务比较简单流程和候选方案，检查业务结果、无效调用以及消耗。用尽预算时仍要能交代已知和未知 |

自主选路与写入权限分别决定。允许助手找会议时间，并不自动包含发邀请的权限。若项目允许发邀请，由实际写入的服务检查发起人、对象和权限。业务要求复核时，定义确认前后的状态，用测试账户核对最终记录和发送次数。[OWASP 关于工具权限与下游授权的指南](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)

## 换项目时怎样验收

选一条典型任务，再选一条能使错误方案露出问题的输入，例如内容相同但用户可读范围不同，或工具返回“未知”而流程规定只能继续查一次。提前写下目标结果、不能发生的动作，以及什么证据足以采用候选方案。指标从本项目取，例如准确回复所占比例、漏分流条数、一次成功任务的费用或入口的第 95 百分位耗时。沿用项目已有门槛；缺少数据时写明待验证，保留现行办法。

比较两种做法时保持输入、起始状态、工具版本和可用预算一致。按项目和关键失败类型分别报告。某类请求平均表现更好时，另列少数会错写、越权或严重超时的结果。换模型、权限或数据分布后，复测受影响的案例；要判断模型波动时，再用[重复试验](repeated-trials.md)。设计演练、模拟执行和真实入口测量分别标明证据来源。
