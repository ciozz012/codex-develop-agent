# 工具调用与写入

设计工具时写清触发条件、结构化参数、返回状态、错误和副作用。优先解析 SDK 的结构化工具调用。由执行层校验参数与当前用户的资源权限，从受信身份上下文取得租户和用户。对外发送、删除等操作按业务授权执行。只要求草稿时，给该流程暴露草稿能力。

## 首次提交前，确定怎样找回这次操作

以“为这次漏水报修建一张工单”为例。执行层在首次发送前保存这次已授权操作的编号、所属账户、动作和原始业务参数，使队列重投、并发处理或服务重启都能接回同一次操作。重试沿用原编号和参数。同号但地址等关键参数变了，报告冲突，保留原请求供核对。用户明确另报一次故障，即使内容相同，也为新意图分配新编号。

查清能否按操作号向工单系统查询最终结果、查询是否可能滞后，以及同号重发在哪个账户、接口和有效期内能去重。核对去重是否覆盖实际写入工单的那一步。如果写入服务由项目控制，可用一次事务将作用域内的唯一操作号与工单一同落库。客户端的提交日志只能帮助恢复，无法单独防止远端重复建单。[AWS 幂等 API 设计](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

## 回执丢失后，执行层根据证据决定下一步

| 当前能确认什么 | 接下来做什么 | 告诉用户什么 |
|---|---|---|
| 权威记录显示原操作已建单，编号为 T-42 | 保存并返回原工单号，结束恢复 | “工单已创建，编号 T-42。” |
| 下游已受理，仍在处理 | 按原操作号或状态地址查询，遵循服务给出的等待时间和查询期限 | “已受理，工单号待确认。” |
| 有可靠证据证明请求从未发出，或下游最终确认未执行且旧请求不会再生效 | 暂时性故障且授权仍有效时，按原意图和接口约定重试。遇到参数错误或业务拒绝，返回具体原因 | 有最终结果再给回执。明确拒绝时说明原因 |
| 写入结果未知，但下游保证在当前范围和有效期内，以原号和相同参数重放不会重复写入 | 有权威查询时先查。仍未知且授权有效时，可在重试预算内按原请求重发。若服务要求等待，先等到允许的时间 | 核实前保留“待确认” |
| 写入结果未知，且去重不可用、已过期或保证不清 | 停止自动写入，保留操作号供后续只读核对或人工查单 | “操作 R-17 暂未确认，可凭此编号核对。” |

若搜索列表尚未同步，一次查无记录只能说明此刻没有搜到。即使是权威查询，也要考虑原请求仍在途的可能。应按重试请求可能抵达下游的时间核对去重期限。给自动重试设定总次数和截止时间，并把已用次数保存在可恢复状态里，避免每次重启都重新计数。达到上限后仍未知就停在待确认。自动重发的 HTTP 语义见 [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)，特定服务对同号参数和保留期限的约定可参见 [Stripe API v1 幂等请求说明](https://docs.stripe.com/api/idempotent_requests)。

## 从正常入口验证恢复

设计时为每种情形写出预期结果，实施时再用隔离数据运行。把回执丢失放在下游提交成功之后、本地记录成功之前。重启处理进程，或让两个处理者同时接手同一个操作。分别核对发送次数、下游实际工单数、返回的工单号和用户看到的状态。允许同号发送多次的接口，一次业务意图仍应只产生一张工单。

再做一组对照。让两个模拟请求都超时、查询都暂时为空，并让下游不提供去重。一个已写入，另一个尚未写入。恢复时，两者都应保持待确认，新增写请求均为零。这样能检验执行层是否真的按当时可见的证据作决定。
