# 用 Codex 开发业务 Agent

沿用项目语言、框架和验证命令。把一个功能的完成条件写成可核查的业务结果，例如“同一次报修重复投递后，工单库只有一条记录，回复中的编号能查到它”。

## 按功能和会话安排工作

| 当前会话 | 工作范围 | 停在哪里 |
|---|---|---|
| 新项目或跨多个功能的目标 | 从真实业务任务拆出可独立验收的功能。每项只列目标、依赖和完成标志。推荐先做哪个，并说明理由 | 交付功能清单和顺序后结束本轮，详细设计与编码留到后续会话 |
| 单个功能的设计 | 选定一个功能，逐步确定业务行为、接口、实现选择、失败处理和验收条件 | 交付该功能的设计、取舍和待决项。实现从后续会话开始 |
| 已选定功能的实现、修复或验收 | 从该功能的入口与验收条件动手，运行必要测试。小改动或单点故障可直接切入相关步骤 | 报告该功能的证据和剩余问题。遇到相邻功能的新需求，将它记入待办 |

用户已点名某一功能或某一步时，直接接续。面对“做完整个 Agent”这样的总体目标，仍从功能清单开始。一轮只推进清单或一个功能的一个阶段。当前阶段结束就交接，等用户发起下一步。即使仍有时间，也保留这个停止点。

首轮拆分时，用“给定什么输入，检查什么结果”检验每一项能否独立交接。例如检索可以检查返回的条款和出处，回答可以给定一条固定条款后核对金额和引用。若两项总要一起运行才能验收，先找它们之间可观察的产物，再决定分开或合并。

## 本轮需要读什么

先从用户请求或上轮交接中确认“当前功能、阶段、待解决的问题”。按下表选择能解答这个问题的材料。整体规划时只用主说明和项目已有索引。功能名称出现在待办清单里，或样例里提到了其他模块，都不构成加载理由。

| 本轮要决定或查证什么 | 按需读取 |
|---|---|
| 工具代表谁操作、谁授予什么权限、在哪一层检查动作和资源，以及怎样验收拒绝路径 | [工具身份与权限](references/tool-authorization.md) |
| 已知用户的可读范围，手册或知识库如何在范围内筛选证据、返回可定位的来源 | [检索可读资料](references/retrieval.md) |
| 验收已有的知识库问答，判断资料在哪一步丢失、回答是否有依据、引用能否支持结论 | [检索质量验收](references/retrieval-quality.md) |
| 模型应传哪些参数、字段缺失或非法时怎么办、调用方根据哪种返回状态继续 | [工具输入输出契约](references/tool-contract.md) |
| 工具如何执行，写操作在超时、重投或恢复后怎样确认结果 | [工具调用与写入](references/tool-execution.md) |
| 单次业务任务应何时交付、继续调用工具、等待事件或向用户追问，怎样识别循环空转 | [单次任务的停止条件](references/run-stopping.md) |
| 用户说“怎么提前停了”，怎样为一次运行留下记录，或从已有记录查出当时看到了什么、哪条规则生效 | [单次任务的运行记录](references/run-trace.md) |
| 故障已定位，怎样把触发条件和应保留的相邻行为做成修复前后都能重跑的用例 | [从故障建立回归用例](references/incident-regression.md) |
| 同一道题有时选对工具、有时选错，怎样重复试跑、比较两个版本并判断改动能否通过验收 | [比较有波动的模型行为](references/repeated-trials.md) |
| 要用模型给答案打分，怎样用人工标注检查评分器会放过哪些错误、会错拒哪些正确答案 | [校准模型评分器](references/judge-calibration.md) |
| 如何从真实入口评价多个环节的业务结果，或区分模拟测试与真实模型评测 | [业务验收示例](references/acceptance.md) |

单项设计用该功能参考里的样例定义验收。只有当前问题确实横跨边界时，才补读对应材料。交接记录给出下轮所需文件的位置，便于对方直接找到原文。

## 逐步设计一个功能

1. 用一条真实请求确定使用者、输入、成功后的可见结果，以及资料不足或操作失败时的结果。
2. 明确本功能负责的决定、读写的数据和需要的上游接口。相邻功能只记录依赖的接口约定，内部设计留给各自的会话。
3. 按执行顺序说明每一步由代码、模型或人完成，以及选择理由。如果不同做法会影响效果，结合一个代表性场景比较准确性、成本、延迟或出错后的恢复，给出建议。已有明确实现时，直接说明依据。
4. 用一个成功样例和一个最能区分方案的边界样例说明怎样验收。影响业务结果或权限的未知项交给用户决策。一个功能仍含多个独立难题时，本轮停在已说清楚的步骤，并标出下次要解决的具体问题。

## 交给一个没有聊天历史的新会话

**收尾。** 在项目已有的任务清单或设计索引中更新当前功能。需要落盘且允许写入、又没有现成索引时，可用 `docs/agent/plan.md`。用下面四行交接，证据指向项目相对路径和具体小节、用例或记录。将设计决定、已实现行为和实际测试结果标清，尚未运行的检查注明“待执行”。

| 交接项 | 写到什么程度 |
|---|---|
| 当前功能与阶段 | 指出本轮完成的范围和停止点 |
| 已定结论与依据 | 设计给出决定及文档位置。已验证的行为给出验证入口、观察结果与适用环境 |
| 待决问题 | 标出哪个问题会阻塞下一步，需要谁或什么证据来解决。其余留在待办 |
| 唯一下一步 | 给出一句可复制的指令，写明索引位置、一个动作、完成标志和停止点 |

**接手。** 按用户最新指令打开索引中的当前项，再打开它指向的证据。先定位上轮决定及其验证状态；如果下一步依赖旧测试，而代码或证据已经变化，就运行最小相关检查或核对当前产物。依据缺失或矛盾时，标出具体缺口，把受影响的结论记为待核实。仅在缺口确实阻塞当前动作时停在这里；独立的待决项留给后续阶段。能确认唯一下一步时，直接完成它并在约定处交接。若有多个可能的当前项且无法从项目确定，询问用户要接哪一项。

**交接验收。** 设想只收到本轮接续指令：能否定位证据、说出待决项，并完成指定动作后停下？缺什么就补到现有索引。纯聊天设计时，把四项直接放在可复制的交接文字里，附上没有文件可查的必要决定。仅在用户要求时创建新聊天或工作区。

## 实现当前功能

- **选择决策点。** 先列出步骤，标出哪一步必须根据中间结果决定下一步。固定步骤用代码编排，动态步骤才交给模型。用户已选框架时沿用它。引入额外 Agent、长期记忆或新协议时，用具体任务说明它要解决的问题。
- **保留定位线索。** 按一次任务关联模型调用、检索、工具结果和结束原因。涉及质量或性能变更时记录版本、耗时和用量。脱敏后再使用真实案例，优先在隔离环境验证有副作用的流程。

## 验证和交付

用软件测试验证执行层的确定性行为，例如身份隔离、并发写入和超时。用 Agent 行为评测从用户入口发起任务，检查实际结果、禁止发生的动作及必要引用。允许多条正确的执行路径。针对波动重复运行代表性任务，列出样本数、运行次数、失败案例和相同条件下的基线结果。修改评分规则或基线时说明原因。

新增 SDK 调用前，根据项目锁定版本核对官方接口。实现阶段使用模拟工具或模型时，标明已验证的范围和还需真实集成确认的部分。

实现、修复或验收阶段交付时，说明实际入口、执行过的检查、观察结果和剩余限制。设计阶段交付验收方法，将测试状态标为待执行。发布、接入生产服务和处理真实数据按当前任务的授权范围执行。
