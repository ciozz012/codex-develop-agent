# 在不同项目上复核选型指导

下面是三个独立的设计演练。比较两个 Skill 版本时，各用无历史的新对话，保持模型、输入和工具条件相同。给受测者当前场景和待测 Skill，将后面的核对表留给评审者。记录每案的回答、遗漏和停止位置。单次演练可发现具体遗漏，多次独立试跑才能观察模型波动。

## 场景

1. **生产质检。** 扫描器发 JSON，字段及状态枚举固定，质检人员已在用规则表，入口 p95 上限 50 ms。用户说「想用 Agent 分流合格与待复核记录，这轮只选方案」。
2. **操作卡问答。** 多包仓库的 `apps/library` 与 `apps/shop` 都有 `work/queue.md`。目标是前者，值班员只能读取当前班组有权访问的有效操作卡。操作卡是有版本的自由文本，最多一次模型调用，资料只读。用户说「只设计查卡后怎样回答，交给从仓库根开始的新对话」。
3. **设施运维。** 固定排查树正在试运行。有些请求须先看一次遥测或工单结果，再决定下一次查哪个系统。当前功能获准读取这两种系统，关停设备另有审批入口。用户说「只设计选择下一次查询的流程，并说明怎么决定值不值得换方案」。

## 核对业务决定

| 场景 | 观察什么 |
|---|---|
| 生产质检 | 方案能解释固定字段和现行规则的用处，用典型输入和异常输入核对分流，按入口 p95 验证 50 ms 约束。区分待测目标与实测结果 |
| 操作卡问答 | 回答有班组可读且有效的版本依据，并处理依据不足。最多一次模型调用，保留只读边界，交接指向 `apps/library/work/queue.md` 中的本功能 |
| 设施运维 | 现行排查树可作为基线，也可扩充明确分支。候选方案只读，能随查询结果选择后续动作，能说明何时停止。在相同任务和预算下比较业务结果、代价及禁止动作后再决定是否替换 |

不同的设计只要能满足本案条件，都可接受。按项目分别记下已满足和缺失的条件；这组演练检查 Codex 的设计建议，线上延迟、真实检索质量和业务工具授权需到对应项目验证。
